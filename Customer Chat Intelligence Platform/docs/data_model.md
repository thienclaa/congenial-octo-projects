# Data Model

## 1. Overview

The data model provides the analytical foundation between the AI labeling pipeline and the Power BI semantic model.

The architecture separates two primary analytical domains:

1. **Conversation / Session data**
2. **AI-generated Chat Labeling data**

Both are persisted in SQL Server before being consumed by Power BI.

```text id="rj4x3m"
                  SQL Server
                      │
          ┌───────────┴───────────┐
          │                       │
          ▼                       ▼
 Fact Conversation       Fact Chat Labeling
          │                       │
          └───────────┬───────────┘
                      │
                      ▼
               Power BI Model
                      │
                      ▼
                Business KPI
```

Production table names, column names, database schemas, and customer-level data are intentionally excluded from this public repository.

# 3. Fact Table 1 — Conversation / Session

The first fact table represents customer conversation or session-level information.

Its purpose is to answer:

> **What happened during the customer interaction?**

The conceptual grain is:

```text id="zq2q38"
One record
    =
One analytical conversation/session event
```

Depending on the production implementation, the fact may contain conversation/session-level operational attributes.

Conceptual fields include:

```text id="5g7h1x"

channel
created_datetime

```

The exact production schema is not exposed.

# 5. Why Separate the Two Facts?

The two facts represent different analytical responsibilities.

### Conversation Fact

Stores the underlying interaction.

```text id="k8w4p2"
Conversation Fact
      │
      ├── Who?
      ├── When?
      ├── Which channel?
      ├── Which session?
      └── What happened?
```

### Chat Labeling Fact

Stores AI-derived interpretation.

```text id="6y2c9a"
Chat Labeling Fact
      │
      ├── What topic?
      ├── Which label?
      ├── What sentiment?
      └── What AI-derived signal?
```

This separation prevents the AI classification layer from being tightly coupled to the underlying conversation structure.


This fact is used for conversation-level metrics.

## Chat Labeling Fact

Conceptually:

```text id="u4v6p2"
Grain:

```

This fact is used for AI classification and sentiment metrics.

# 15. Grain and Duplicate Prevention

Because the two facts can be joined through shared identifiers, duplicate records must be controlled.

For example:

```text id="1c9r5w"
Session 1001
     │
     ├── Conversation Fact
     │
     └── Chat Labeling Fact
```

If either fact contains multiple records for the same analytical grain without being intentional, measures such as session counts can be inflated.

Therefore, the semantic model should use measures and relationships that respect the defined grain.

A common approach is to use distinct session counting where appropriate.

---

# 17. Customer-Level Metrics

Customer-level metrics require a different aggregation grain.

For example:

```text id="k3p8s6"
Total Customers
=
Distinct Customer IDs
```

A customer can have multiple sessions:

```text id="z1c7h5"
Customer A
   │
   ├── Session 001
   ├── Session 002
   └── Session 003
```

Therefore:

```text id="w9f2m4"
3 Sessions
≠
3 Customers
```

This distinction is essential when calculating customer-level sentiment or complaint metrics.

---

# 18. Negative Customer Logic

A negative customer metric should not simply count negative sessions.

Conceptually:

```text id="2x6r8j"
Customer
   │
   ├── Session 1 → Neutral
   ├── Session 2 → Negative
   └── Session 3 → Positive
```

This customer should be counted as a negative customer because at least one session was classified as negative.

Therefore:

```text id="h5q8n1"
Negative Customers
=
Customers with ≥ 1 Negative Session
```

This differs from:

```text id="r3m7k2"
Negative Sessions
=
Number of Negative Sessions
```

The distinction prevents session-level volume from being incorrectly interpreted as customer-level impact.

# 23. Analytical Questions Supported

The model is designed to answer questions such as:

### Conversation Volume

* How many conversations occurred?
* How does volume change over time?
* Which channels generate the most conversations?

### Customer Sentiment

* What percentage of sessions are negative?
* Which categories generate the most negative conversations?
* Which channels have the highest negative rate?

### Customer Experience

* How many customers experienced a negative interaction?
* Which complaint categories occur most frequently?
* Are complaint patterns increasing over time?

### Commercial Analytics

* How many conversations are related to orders?
* Which customer intents are associated with purchasing?
* What is the relationship between chat activity and order conversion?

---

# 24. Why This Model Supports BI

The separation between raw conversation context and AI-derived attributes allows the semantic model to combine:

```text id="p2v6k8"
Operational Data
      +
AI-derived Data
      +
Business Dimensions
      ↓
Business Analytics
```

This means Power BI does not need to understand how the LLM works.

Power BI only consumes the structured analytical output produced by the upstream pipeline.

---

# 26. Summary

The data model establishes a clear separation between:

```text id="j5r9w2"
Conversation Data
       │
       ▼
Fact Conversation

AI Interpretation
       │
       ▼
Fact Chat Labeling

Shared Analytical Context
       │
       ▼
Dimensions

Business Logic
       │
       ▼
Power BI Semantic Model
```

The result is a reusable analytical structure that allows unstructured customer conversations and AI-generated classifications to be transformed into standardized business metrics.

The key design principle is:

> **Store AI outputs as structured analytical data rather than treating the LLM response itself as the reporting layer.**
